## Commands to run

Every command runs from the repository root, with `fvm`, never a bare `dart`. None of them starts `flutter`: no committed case runs it, and the package's tests run a seeded `flutter` case only against a stand-in SDK (`standInSdk`), or against a `dart` that belongs to no Flutter SDK (`plainDart`) to pin its absence.

One-time setup on a fresh checkout:

```sh
fvm install            # reads .fvmrc: Flutter 3.47.7, which bundles Dart 3.13.5
fvm dart pub get       # resolves the whole workspace into the committed root pubspec.lock
```

The gate:

```sh
fvm dart pub get --enforce-lockfile && fvm dart analyze --fatal-infos && fvm dart run nidana_contract_check --all --set structure && fvm dart test packages/nidana_contract_check
```

The gate checks the `structure` set over the nine committed contracts and runs the package's tests. Those tests replay the seeded `gen` slug's file replay and recorded invocations against a stand-in generator package in a temporary workspace. The gate runs neither `--set file` nor `--set cli` over the committed tree: every committed-tree line below comes from the replays that follow it, and every line about a seeded defect comes from the tests.

The phase's Verification, which the gate does not run over the committed tree. The first two replay the file set and the cli set of every slug; the third replays the two contracts whose producers do not exist; the fourth and fifth are the restricted gates of the producing phases that will admit part of them; the sixth replays every set of every slug; the last runs the seeded file and cli cases against the stand-in generator:

```sh

```

The phase produces no contract, so there is no output of its own to validate against a schema. The checklist for the diff, where `cdb110c` is the parent of Task 1's commit:

An unreadable entry only one side holds is also `missing-file` or `extra-file`; an unreadable tree root reads as the file `.`. Without `expected/`: `output ({output} exists after the run, expected nothing there[: {files, ascending, separated by commas}])` or `output ({output} is a file, expected nothing there)`. With `expected/`: `output (nothing at {output}, expected the tree of expected/)`, `output ({output} is a file, expected the tree of expected/)`, or `format (dart format exited {code}[: {first stderr line}])` and the tree problems of a file replay. Task 6's `readTree` would have had to throw, ending the whole replay with exit 2 and no fixture line for any slug, or drop the entry, which would be reported as `missing-file` or `extra-file` or not at all. Ruling: `FileTree` maps a path to a sealed `FileEntry` (`FileBytes` or `FileUnreadable`); the pure comparison reports an unreadable entry on either side as its own problem, `unreadable-file ({path} in expected|output: {reason})`, never equal and never a throw; an unreadable entry that only one side holds is also `missing-file` or `extra-file`; and `readTree` never throws and records each kind it cannot read. The reason is that ADR-001 item 6 compares the file set byte for byte, so a generator that writes an entry nobody can read produced a wrong tree, which is a case FAIL, not an environment error. Pinned by `tree_test.dart` (the group `an unreadable entry`, 5 tests), `file_set_test.dart` (`an entry the shell could not read is an unreadable-file problem`), `command_test.dart` (the rule labels) and, for `readTree` over each kind, the group `readTree` of `command_runs_test.dart` and the tests `a directory the generator leaves unreadable fails the replay, ...` and `a directory a command leaves at {output} that cannot be listed fails the case, ...`.
  - `pub get` precedence (Task 5). `dart pub get --enforce-lockfile` runs whenever a plan holds a file replay or a recorded invocation, even when the restriction admits no case of them, and its failure exits 2. ADR-001 item 9 says the `pub get` runs "before the file or cli set", and every gate already runs `fvm dart pub get --enforce-lockfile` first, so the order never changes a gate's outcome. If the ruling were wrong, a restricted replay of a broken workspace would exit 2 instead of passing unrun. Pinned by `pub get runs, and its failure makes the file set unavailable (2), even when the restriction admits no file replay` and its cli twin in `command_runs_test.dart`, and by the group `the one pub get of a replay` in `cli_test.dart`.
  - Contract text (Tasks 3 and 4). A contract text that is absent or not UTF-8 fails the file replay and every cli case as `command (no contract text at {path})` or `command ({path}: not UTF-8: ...)`, admitted or not. The plan's briefs list no contract-text defect for the cli set, which reads the text only for the Case table's ids; this is a reading of decision 12 (a fixture defect fails before admission, and a case that cannot read its ids would otherwise run unrestricted with none). The wording is Task 3's ruling, carried to Task 4. Pinned by `a contract text that is not UTF-8 fails with its reason, not as absent` in `file_set_test.dart` and `a contract text the set cannot read fails every case, admitted or not` in `cli_set_test.dart`.
  - Package configuration (Task 5). A package configuration holding a root that is not a plain `file:` URI (an empty authority, no `%2F` in a decoded segment) is refused as a whole: the existing exit-2 path, `.dart_tool/package_config.json is not a package configuration`, never 255 or a crash. The alternative was dropping the root, which would print `package X is absent` for a package the configuration does configure, and PENDING (exit 1) reads as "the producer is not written yet", not as an environment defect. pub never writes such a root, so only a hand edit reaches this. The side effect is that surface, reject and behavior are unavailable on such a configuration too, where they used to accept its names. Pinned by `a package configuration with a root that is no plain file: URI is no package configuration (2)` in `cli_test.dart`, `a configuration with a root that is no plain file: URI is no package configuration` in `packages_test.dart` and `the roots packageRootsOf gives read as file paths, and a root that is no plain file: URI throws` in `command_test.dart`.
  - Temporary directories (Task 6, carried into Task 7). Deleting a run's `{t}` is best effort: a progress line, `could not delete {t}: {reason}`, goes to stderr when one cannot be deleted, and the case's outcome stands. If the exception were let out, `runCli`'s handler would end the whole replay with exit 2 and undo the ruling that a tree a generator made undeletable is a case FAIL. Pinned by the two tests named under the first deviation, which assert the line.
  - Tests (Tasks 6 and 7). Every `chmod 000` test is skipped as root (`skipAsSuperuser` in `test/support/seed.dart`: the superuser reads what mode 000 denies, so the test could not see what it pins): five tests, four in `command_runs_test.dart` and one in `behavior_cli_test.dart`. OS-worded reasons are pinned by prefix only (`unreadable: Cannot resolve symbolic links: `, `Cannot open file: `, `Directory listing failed: `), because another libc words them differently (musl says "Symbolic link loop"). Pinned by the `readTree` group and the two file and cli tests that leave a directory unreadable.
  - The `{output}` link reading (Task 7). A link at `{output}`, even one to a directory, reads as `{output} is a file`: the brief reads what is at `{output}` with `typeSync(followLinks: false)`, and a case with `expected/` then fails even when the link points at the right tree. `readTree` itself reads links through, and the file set compares through a linked root. This is a reading of ADR-001 item 7's "the tree at `{output}`". Pinned by `what is at {output} after the run: a file or a link is a file, and nothing is nothing`.
  - Files outside a brief's list, all test code or dartdoc inside the package: `behavior_cli_test.dart` (Task 1: its test pinned the exit 2 that decision 19 removes, so it was rewritten, not deleted) and `cli_test.dart` (Tasks 6 and 7: the beyond-the-brief assertions that pinned `notImplemented` after a passing `pub get`), `test/support/seed.dart` (`skipAsSuperuser`; `runTool`'s optional `environment`) and `lib/src/workspace.dart` (dartdoc: the count of `dart:io` libraries moved to `test/purity_test.dart`).
- Choices where the plan or the briefs left room, with the reason for each:
  - Records are read through links, as sources are (Task 1). A dangling link at `invocation/{case}/args`, `exit_code`, `stdout`, `stderr` or `files/analysis_options.yaml` ends the whole command with exit 2 (`--set structure` and `--all` included), while an absent record is a case FAIL. Decision 10 covers a missing file, not a dangling link; the alternative was reading records only for a plan that holds the cli set. Pinned by `a record is read through a link, a dangling one throws, and a hidden case holds none` in `cli_test.dart`.
  - The suite files are read with `File.existsSync()` and no hidden-name filter (Task 1), so a suite imported through a hidden name or a linked `behavior/` is read for another slug's suite though `readSnapshot` would not read it for the replayed slug. No committed fixture has either.
  - A script path built from segments (Task 2). `processOf` builds `{root}/bin/{executable}.dart` with `Uri(pathSegments: ...)`, not `resolve('bin/{executable}.dart')`: `readArgs` admits an executable holding `#`, `?` or `%`, which the string form would turn into a fragment, a query or a decoded byte and throw on, crashing the shell on a defective recording instead of failing its case. Pinned in `command_test.dart`.
  - Reading `args` and the plugins (Task 2): a `\r` stays part of its line (decision 10, "every other line one argument as written"), so a CRLF `args` is unreadable and the defect is loud; a whitespace-only line inside `plugins:` neither ends the section nor sets its indentation.
  - Substitution is one pass (Task 3): an `{output}` inside the input path, or the reverse, is never substituted again. Paths compare in code-unit order.
  - The first row of the Case table naming a case supplies its ids (Task 4); a duplicate row is ignored, which structure does not flag and no committed contract has. A malformed Covers cell gives no ids, so the case runs only unrestricted. The `exit_code` text is `0` or a decimal without leading zero up to 255 with an optional final newline; a longer number is a defect, not a throw.
  - The `format` detail's first stderr line is not run through the placeholders (Task 4, as the file set words it): it names `dart format`'s own message and varies from run to run. The `exit` detail's stderr line is.
  - `readTree` walks one directory at a time and judges each entry by `typeSync` with links followed (Task 6): `listSync(recursive: true)` throws on the first unlistable directory and loses the rest, and reports a pipe, a socket and a device as files, and reading a pipe blocks. A link to a directory already on the current descent, by resolved path, is a cycle; a link to a directory elsewhere is read again, so two links to one directory give both copies, and a diamond of links is read once per path (no committed fixture holds a link). An unlistable root is keyed `.`, so a report never prints an empty path. A pipe and a device are never opened.
  - A generator's stdout and stderr are not printed (Task 6): only the `exit` detail carries the first stderr line, which keeps stdout to one line per fixture (ADR-001 item 9).
  - The cli set resolves every run to its process before any case starts (Task 7), so one that cannot be resolved (no flutter) makes the slug's set unavailable with no case started, not even the runs before it. The forms of `{output}`, `{files}` and `{root}` are built before the command starts, so a command that deletes its own `files/` cannot make the resolution throw, and `expected/` is read after the run, as the file set reads it. A `{package}:{executable}` run whose package the configuration lacks gets its own reason from `runCliSet` (`package {package} is absent from ...; {path} runs {package}:{executable}`), which the shell never reaches, because the planner already made such a run PENDING from the same configuration; a direct test pins it.
  - No process timeout (decision 17, routed): a child's stdin is at end of input, so a command waiting for input cannot hang the gate, but one that never exits still would.
  - A generator or a command that writes outside `{output}` is not detected, and a recorded invocation runs in place in `invocation/{case}/files/` (it must: the committed `analysis_options.yaml` files enable the plugin by a path relative to `files/`), so a command that writes there leaves files `.gitignore` would hide (a `.dart_tool/` or a `pubspec.lock`). ADR-001 items 6 and 7 require neither check.
  - The two sets and their new libraries (decision 18): `processes.dart` is the one way the tool starts a process and `command_runs.dart` runs both sets; `purity_test.dart` pins the five libraries that import `dart:io` and now follows an own-package `package:` import. `command_runs.dart` reached 587 lines and `cli_set.dart` 530, within the plan's file map; neither was split.

## Outstanding

The real producers do not exist, so the file and cli sets ran for real only against the stand-in generator `gen` and the seeded `dart analyze` case. topic-codegen@v1's file replay and its 22 recorded invocations, and nidana-checks@v1's 17, are `PENDING` on the committed tree: none of the 39 committed cases has run for real. Three things are therefore unverified until nidana.tooling's packages exist: that the real `nidana_dart_codegen` and `nidana_dart_lint` produce what the recordings hold; that the recordings' `{files}` and `{root}` paths match what the tool substitutes (the seeded recordings pin the substitution, the committed ones have never met it); and that a recorded invocation run in place in `invocation/{case}/files/` leaves nothing behind (the eight `analyze-*` cases first load the real plugin through their `files/analysis_options.yaml`, and the tool does not detect a command that writes there). ## Learnings

- ADR-001 item 9 gives one `dart pub get --enforce-lockfile` so no case runs on a stale resolution, and nidana.model.7's Scope (4) gives as its reason that `dart run` from a `files/` directory exits 255 on one; the gate shows the reason does not hold: `pub get` rewrites neither `pubspec.lock` nor `.dart_tool/package_config.json` when the resolution is unchanged, so after the gate's own `pub get` this repository still reads stale (`dart run nidana_contract_check nosuch` from `scan-clean/files/` exits 255 with `Could not find a file named "pubspec.yaml"`, as `staleness2.sh` M5 recorded) and the cli test `a workspace whose resolution reads stale still runs every case` shows `dart run gen:generate` from a case's `files/` exits 255 after the replay's `pub get`; the tool runs `{package}:{executable}` as the package's `bin/{executable}.dart` under the running `dart` with `--packages` instead (decision 1), which runs either way, and the same finding touches nidana-checks@v1's Validation sentence "resolves nothing in place" (the contract gap of `docs/auto-run/steps/S121.json`). Disposition: dropped (routed to the end-of-node governance sweep for ADR-001 items 7 and 9)
- A recorded invocation runs in place in `invocation/{case}/files/` (ADR-001 item 7 says `files/` "becomes the working directory"), which the committed `analysis_options.yaml` files require, as they enable the plugin by a path relative to `files/`; the tool does not detect a command that writes there, and `.gitignore` would hide a `.dart_tool/` or `pubspec.lock` it left. Disposition: dropped (routed to the end-of-node sweep's ADR-001 item 7 touch)
- "The backticked span ... that holds `{output}`" (ADR-001 item 6) names three spans of topic-codegen@v1's `- file:` bullet, the command and `{output}` alone twice, and the tool reads it as the one that also holds a space, because a command has a program and an argument (decision 3; `the committed topic-codegen text names one generator command` in `contract_test.dart`). Disposition: dropped (routed to the end-of-node sweep's ADR-001 touch)
- A plugin a case's `files/analysis_options.yaml` enables is read as a package its command runs, because `dart analyze` runs the plugin and without it nidana-checks@v1's eight `analyze-*` cases would run and fail on the exit `dart analyze` gives for a plugin that does not resolve instead of being PENDING (decision 11; the committed-tree replays show all eight PENDING on `nidana_dart_lint`). Disposition: dropped (routed to the end-of-node sweep's ADR-001 touch)
- For file replays and recorded invocations the restriction is decided before PENDING, unlike the behavior set, because a `file` or `cli` contract may have several producing leaf-parents whose gates restrict to their own shares and no producer waits on another (decision 12; the restricted `nidana-checks` replay shows its `scan-*` cases pass unrun while its `analyze-*` cases are PENDING). Disposition: dropped (routed to the end-of-node governance sweep for ADR-001 item 9)
- nidana.model.6's verification doc says a read defect in a suite slug's tree ends the replay of the replayed slug, and it ended the whole replay with exit 2 and no fixture line for any slug (reproduced by Task 1's failing tests); this phase reads only the suite files, and Expected output states the corrected behavior. Disposition: dropped (a verification doc under hsdd/verify is not edited by a later phase and this doc states the correction)
- A generator or a command that writes outside `{output}`, or a recorded invocation that leaves files in its `files/`, is not caught, because the tool compares only the tree at `{output}`, the exit code and the recorded streams. Disposition: dropped (ADR-001 items 6 and 7 do not require it)
- A generator or command that never exits hangs the gate, because the tool starts every process with no timeout; a child that waits for input cannot, because its stdin is at end of input (decision 17). Disposition: dropped (ADR-001 requires none and it stays routed to the first gate that runs a suite with timers or isolates)
