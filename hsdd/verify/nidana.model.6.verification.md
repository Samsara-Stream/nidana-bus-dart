## Outstanding

The real `flutter test --no-pub` was never started. This machine's Flutter SDK has no engine artifacts (`bin/cache/pkg/sky_engine` and `bin/cache/artifacts/engine` are absent), and fetching them is a network action outside the run rules. The Flutter runner was verified only against a stand-in SDK whose `flutter` runs `dart test` (`standInSdk` in `test/support/runners.dart`). That pins what the tool controls: which bindings it gives to flutter, which executable it starts, the exact arguments (`test --no-pub --reporter json`, then `--name` and the filter when restricted, then the binding's path) and how it reads the report. That the pinned flutter runs a binding under `hsdd/` from the pure-Dart workspace root with `--reporter json` and `--name` as the tool calls it rests on flutter_tools 3.47.7's source (`docs/auto-run/experiments/behavior-set-plan/`, T3) and on `contract-fixtures` Q10 and Q11, which ran on another machine. Because the stand-in prints package:test's protocol, three facts about the real flutter's output are also unobserved, and the reader's handling of each is a reading of the source and of `dart test`'s output:

- whether flutter prints non-JSON text on the same line before a JSON event (the reader reads such an event from its first `{"`);
- whether a load failure starts `Failed to load "{path}":` as `dart test`'s does (the reader falls back to the whole error text when the prefix is absent);
- what flutter prints, and what exit code it returns, for a `--name` filter that matches no case (the tool never starts a runner with a filter that admits no case of the binding's suite, but a binding that registers its cases under other names reaches it, and the reader then fails it as `no case ran` whatever `done` says).

Proposed disposition: deferred to nidana.flutter.2, whose gate `fvm dart run nidana_contract_check flutter-binding --guarantee G9` is the first to start the real flutter through the tool (nidana.flutter.1 needs the artifacts first, to resolve its Flutter member).

## Learnings

- The phase Verification says topic-model@v1's cases fail "on `UnimplementedError`", and the gate shows it holds for 27 of the binding's 32 failures: the other 5 fail on expectations, G7, G8 and G13 on the `==` that stays `Object`'s, G17 on the `toString` that stays `Object`'s and G4 on a parent correlation ids list the envelope keeps uncopied, all of them what the type-level phases leave undelivered. The binding loads. Disposition: dropped (nidana.model D3 decides it; nidana.model.8 delivers the equality, the source rendering and the copies)
- An `--guarantee` id that its slug's contract does not declare is now a usage error (64) that the replay reports before it reads anything; ADR-001 item 9's list of usage errors (an unknown slug or set, a malformed id, a bare `G{n}` with more than one slug) does not name it. Disposition: dropped (item 9's list begins such as; an ADR-001 touch may name it)
- ADR-001 item 9's description of the `structure` set names neither of the two rules this phase added, `encoding` (a Dart source that is not UTF-8 fails at its path) and `conformance-import` (item 4's ban on a conformance library importing a test package, which item 12 already puts under `structure`). Disposition: dropped (routed to the end-of-node sweep's ADR-001 touch)
- A conformance library that no binding in any slug imports would cover nothing, and the tool does not check it, because that needs a cross-slug view. The gate shows no committed suite is unbound: each of the nine conformance libraries under `behavior/` is imported by at least one of the ten bindings (`navigation_executor_conformance.dart` by two). Disposition: dropped (routed to the end-of-node sweep, no committed suite is unbound)
- The runner process is started with no timeout, so a binding whose case never yields hangs the gate. Disposition: dropped (ADR-001 does not require one; routed as a note)
- The phase plan estimated about 300 lines in about 5 files, tests included; the product diff is 3927 lines inserted (194 deleted) in 28 files, 1428 lines in 14 files of library code and 2499 lines in 14 files of tests, about 13 times the lines and 5.6 times the files, a sizing finding for the node's remaining phases. Disposition: dropped (sizing is the owner's to revisit at a checkpoint)
