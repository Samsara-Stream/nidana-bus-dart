## Request

The owner accepted Specification v0.15.1 (dated 2026-10-18, header still Draft) on 2026-10-20 as the normative Specification for v1, replacing v0.15.0 (DEC-685), and asked that every decision and every artifact of the tree be brought in line with it. The Guide and the Rationale v0.15.1 stay informative. v0.15.1 rewrites the startup barrier (Spec §3.13), adds scope timing (§7.2), makes the write chain the unit an error terminates (§10.2), names the fields of the runtime name check (§4.3) and adds a module wrapper widget on Flutter (§7.3); the Guide adds Dart notes on replay timing (§6.1), transformer naming (§6.3) and catalogs without reflection (Appendix C.1). No phase has shipped, and the request sets no date.

## Routing

### Class and shape

`cross-node`. v0.15.1 changes guarantees of five contracts (topology-dsl, bus-api, bus-testing, navigation-api, flutter-binding), the decision text of ADR-003, and the specs or plans of six nodes; it fits inside no single leaf-parent, so it is not `local`.

The tree's shape holds, so it is neither `new-capability` nor `structural`:

- The startup barrier's new machinery, which Guide §6.1 describes as topic storage and fan-out owned by the bus, or a wrapped subject, with RxDart kept for operators, is internal to nidana.runtime. RxDart stays the operator engine, so ADR-002's signal for splitting the runtime package (a v1 requirement for a second engine) is not met, and root D3 and D4 stand.
- The connection order at `start()` (writers before readers) is a computation over the read/write graph of the bootstrap activations. It stays inside nidana.runtime; topology-ir@v1 Versioning would take a new analysis function compatibly if the bus-api handoff asks for one, which changes no contract set.
- `NidanaModule` (Spec §7.3, Appendix A.8) is a widget of the existing Flutter adapter package, `nidana_dart_runtime_flutter`, owned by nidana.flutter and declared, if v1 takes it, by flutter-binding@v1.
- No node, contract or ADR becomes empty, wrong or missing. No node is as-built, so nothing is promoted. `hsdd/management/` held no intake record, so nothing collides.

### Landing

Each item names the passages of v0.15.1, the current text they contradict or leave incomplete, and where the change goes. "Spec", "Guide" and "Rationale" mean v0.15.1. The baseline is cited as Spec v0.15.0 where needed. Section numbers did not move between the versions. The RxDart bullet sits in Spec §3.3, not §3.6.

**L1. The startup barrier and replay during bootstrap.** Spec §3.13 (rewritten), §11.2 item 2, §2.1 "Replay timing", §3.3's RxDart bullet, §2.5's `getCurrentValue()` contract; Guide §6.1 "Dart: replay is asynchronous", §6.5's Dart/RxDart row. During bootstrap `activate()` and `publisher()` validate and claim at once, a topology gets its handle but is not connected, a `bus.observe()` subscription is not connected, nothing replays, and shell publishes are queued. `start()` first connects the bootstrap topologies in topological order of their read/write graph (a writer before every reader, ties in activation order, each first emission seeing inputs its writers have settled) and the bootstrap subscriptions, then delivers the queue in global publication order, each envelope keeping its publication timestamp.

- Contradicts bus-api@v1: the delivery rule "The connection" ("It reaches the reads before `activate` returns ... It is not a publish; the startup barrier does not hold it back"), G22 ("The connection reaches the reads before `activate` returns"), G34 ("every topology activated before `start()` is connected when `start()` delivers the queue (G22)"), G17 for a subscription made during bootstrap (first values "in the first provider-zone microtask after `listen` returns"), and Versioning amendment (a). It supersedes DEC-166 and the bootstrap reading of DEC-158.
- Reaches ADR-003 item 6, first bullet ("including the first delivery of state and replay topics, which comes in a provider-zone microtask (bus-api@v1 G17 ...)").
- Reaches topology-dsl@v1 Live interpretation item 3, G19 and G24 ("seeds its fold with the topic's current value at activation"); bus-testing@v1 G14 and G19 (`OrderingProbe` starts "with what bus-api@v1 G17 delivers first"); navigation-api@v1 Refinement 8, G14 ("once its activation has connected (bus-api@v1 G22)"), G19, G24 ("this rests on bus-api@v1 G22 and G34") and the `nav.access-policy` paragraph (an app "publishes its first policy before `start()`"); flutter-binding@v1 Refinement 2, Refinement 5, G5, G6 and G16.
- Reaches nidana.runtime D3 ("Activation emits a read's connection from the cell's current value or buffer before `activate` returns"), its "Inherited from the root" first bullet, plan decision D8 and phases nidana.runtime.6, .7 and .12; root D9; nidana.flutter's Overview; nidana.navigation.6; nidana.integration's bootstrap slice and nidana.integration.4.
- Consistent, no change: bus-api@v1 G8 (publishes queued before `start()` are not reflected), G35 (the window is a provider-zone timer), and the delivery rule "A publish" (the envelope and its timestamp are made at the publish).

**L2. Scope timing.** Spec §7.2 "Scope timing", §7.1's APPLICATION row, §3.13's last paragraph. A MODULE or PAGE activation before `start()` is rejected with a diagnostic naming the topology; an APPLICATION activation after `start()` works, and dev mode reports that EventTopic events published before it were not delivered to it.

- Incomplete in bus-api@v1: G34 ("meanwhile `activate`, `publisher`, `observe`, `module` and `addObserver` work") states no rejection; G28's acquire activates at any time; G22's `LateApplicationActivation` carries the topology id only.
- Reaches flutter-binding@v1 G8 and G10 (activation at mount, acquire at `didPush`), G17 and "How an app uses it", whose widget test "pumps `t.wrap(page)`, calls `t.bus.start()`"; nidana.runtime.11 and .14; nidana.integration.5's page widget tests and nidana.integration.7.
- The rejection belongs to bus-api: a new `TopologyFinding` variant would be breaking under topology-ir@v1 Versioning (its finding family is closed, G1), and CI cannot see when an activation happens relative to `start()`.

**L3. The write chain.** Spec §10.2 principles 2, 4 and 5 (first bullet and closing paragraph), Appendix A.4 "Write chain", §3.10's first atomicity bullet. The first unhandled error in the pipeline one `write(topic, stream)` declaration connects to its topic ends that chain; the bus cancels the chain's subscription, reports it in dev mode and never restarts it; the error never reaches a topic; the topology's other chains keep running and its claims stay until deactivation; this holds on Dart, whose streams continue after an error event.

- Incomplete in topology-dsl@v1: Errors and lineage ("An error that reaches a sink ends that sink for the rest of the activation: it publishes nothing more, the topology's other sinks go on") and G26 say nothing of cancelling the chain's subscription and the stages, inner subscriptions and timers that feed no other live chain.
- Reaches bus-api@v1 G26 and `PipelineTerminated` (one per sink); nidana.runtime.9, .10 and .12.

**L4. Errors in shell subscribers.** Spec §10.2 principle 5 (third bullet and closing paragraph), §3.10's first atomicity bullet. A `bus.observe()` callback that throws stops neither the other subscribers nor the publish, and its exception goes to the uncaught-error handler of the zone in which `listen` was called. An exception raised by the bus's own delivery code is a defect and is not swallowed.

- Contradicts ADR-003 item 2, second bullet ("a subscriber's callbacks run there whatever zone it listens from") and its Consequences ("errors in those callbacks reach the error zone the bus was constructed in").
- Contradicts bus-api@v1 G5, G18 ("its error going to the provider zone's uncaught-error handler") and G41 (a conversion's `TypeError` "goes to the provider zone's uncaught-error handler, as a throwing subscriber's error does"); reaches bus-testing@v1 G4 and G11, flutter-binding@v1 G5 ("nothing reaches the provider zone's uncaught-error handler"), nidana.runtime D5 and nidana.runtime.6, nidana.navigation D6 ("which bus-api@v1 G18 sends to the provider zone's uncaught-error handler").
- Left to decide: whether G41's conversion of an off-type value at a topology read is the bus's own delivery code, a read-stage error that ends the chain (L3), or a reported skip as now.

**L5. The runtime name check.** Spec §4.3's runtime row, §3.1, §2.1. The registry is keyed by name; the first use of each declaration is compared with the registered one; any difference in variant, payload type, sensitivity, deduplication or replay size throws, naming both; equal declarations share one subject; initial values are not compared; `removeTopic` frees the name.

- bus-api@v1 G7 compares the same fields plus tracing; v0.15.1 neither lists nor excludes tracing. v0.15.1 adopts DEC-168 except for tracing.
- Consistent: G41 and nidana.runtime D4 (keyed by name), topic-model@v1 G7 (equality by variant, name and value type, the `(name, type)` identity of §2.1 and §3.1).

**L6. Re-activation of a topology on Dart.** Guide §6.3 "Name every transformer", reading Spec §3.9 (unchanged): re-activation compares transformers, a Dart closure equals only itself, so a second activation of a topology whose `declare()` passes an inline lambda throws; tear-offs of one top-level or static function are equal.

- Contradicts bus-api@v1 G23 ("including two that differ only where a definition does not look (a scan seed, a closure body, two functions rendering one name)") and DEC-167. The runtime fact is settled: `docs/auto-run/experiments/function-ref-derivation/output.txt`, "two closure evaluations equal: false".
- Reaches flutter-binding@v1 Refinement 4 and G8 (holder counts per topology id, DEC-253) and nidana.runtime.11; nidana.navigation D5 (the resolver names its stage functions) already follows the Guide.

**L7. The module wrapper widget.** Spec §7.3's Flutter row and Appendix A.8; Guide Appendix B.3's `NidanaModule(topology, child)` (unchanged). Flutter binds module scope through a route observer with a prefix match, or through `NidanaModule`, which acquires on mount and releases on unmount, needs no route names and works with any router; covered routes stay mounted, so the count stays above zero while a route of the subtree is on the stack.

- flutter-binding@v1 declares no wrapper (G1's export list, G2's "four widgets"; Refinement 1 leaves an app on go_router to implement `NavigationRouter` itself, while `ModuleScopeObserver` needs routes that carry names).
- flutter-binding@v1 Refinement 3 (stack membership) is what v0.15.1 now states: DEC-249 adopted.
- Reaches nidana.flutter's Purpose and Owns, nidana.flutter.1 and .6, nidana.integration's module slice, root D1's Flutter adapter row.

**L8. Replay timing on a running bus.** Spec §2.1, §3.3, §2.5; Guide §6.1, §6.5. A Dart subscriber receives its replay one scheduling boundary after `listen`, ahead of later values. This matches bus-api@v1 G8 and G17 after `start()`, nidana.runtime D3's synchronous topology read path, and ADR-003 item 9. Root D9's upstream mark on Spec §3.3's RxDart bullet (DEC-032) is adopted. Text only: root D9, nidana.runtime's "Inherited from the root", ADR-003's Context.

**L9. Catalogs without reflection.** Guide Appendix C.1 "Platforms without runtime reflection". The explicit list matches nidana.tooling.codegen D1's registration library (DEC-365) and root D1's deferral of orphan and unreachable-topic analyses to v2. No contract changes; nidana.tooling.codegen D1 records the Guide's adoption.

**L10. Explicit transformer names.** Guide §6.3's last sentences. topology-dsl@v1 keeps "an explicit transformer name on a combinator" under "Not in v1": no v1 consumer compares `FunctionRef` labels across compilation modes or under `--obfuscate`, and nidana.integration D8 keeps the example's transformers public so the JIT catalog equals the AOT graph (topology-ir@v1 "Private names"). No change; the topology-dsl handoff records it.

Unchanged except citations: topic-model@v1, topology-ir@v1, topic-codegen@v1, nidana-checks@v1, ADR-001, ADR-002. The Rationale changes companion links only.
