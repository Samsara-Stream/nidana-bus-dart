# ADR-001: Executable validation for Dart API contracts

## Context

HSDD lets a contract be `stable` only when it carries an executable validation artifact, a schema or a fixtures directory, at its canonical paths. The gate of every producing phase replays that artifact, and consumers build against the fixtures instead of hand-rolled mocks. HSDD's per-kind defaults (a schema plus example payloads for `api`, a schema plus edge cases for `shared-model`) fit wire formats. Most contracts in this tree are Dart library surfaces instead (root contract matrix): topic-model@v1 is `shared-model`; topology-dsl@v2, topology-ir@v1, bus-api@v2, bus-testing@v2, navigation-api@v1 and flutter-binding@v2 are `api`; topic-codegen@v1 is `file`; nidana-checks@v1 is `cli`. Their guarantees come in two sorts. Some are type-level, because the Specification makes the misuse a compile error: an event topic has no current value (Spec §2.5), an observer has no publish path (Spec §3.7), a read handle has no synchronous value (Spec §6.1). The rest are behavioral, above all the Bus Runtime Contract (Spec §3). Root OQ8 asks what executable validation means for such contracts.

Three properties of the setting shape the answer:

- Contracts and their fixtures are authored before any producing package exists. A fixture is a forward reference until the contract's first producing phase, the first phase of its producing leaf-parent that its `produced_by` names, lands the declarations of its Interface (root D10, ordering policy `fp-progression`).
- One interface can have implementations that need different test runners. The navigation executor protocol is implemented on the VM by an in-memory router and in Flutter by `FlutterNavigationExecutor`.
- The repository is one pub workspace whose root also holds `hsdd/` (ADR-002).

The experiment `docs/auto-run/experiments/contract-fixtures/` (`run.sh`, captured in `output.txt`) reproduces that layout on the pinned SDK (Flutter 3.47.7, Dart 3.13.5) and settles the runtime facts this decision uses:

- `analyzer: exclude: [hsdd/**]` in the root `analysis_options.yaml` keeps fixtures out of a workspace-wide `fvm dart analyze`, while an explicit path into `hsdd/` is still analyzed (Q1, Q2). A nested `hsdd/contract/fixture/analysis_options.yaml` replaces the root's lint set for every fixture; without it, the root's `depend_on_referenced_packages` fires on every fixture import, because fixtures belong to the root package.
- `fvm dart analyze --format=json` reports each diagnostic's code in lowercase, the spelling `// ignore:` comments use, with its 1-based line, at every severity: errors, warnings such as `invalid_use_of_visible_for_testing_member`, and infos (Q2, Q3). With `--fatal-infos`, a deprecated member fails a surface fixture; with the strict language modes, so do raw types and inference failures (Q5).
- A reject fixture written without running the analyzer can name the wrong code: the plausible `final_class_extended_outside_of_library` is reported as `invalid_use_of_type_outside_library` (Q7). Matching each expected code to a line also catches a marker on the wrong line and extra diagnostics, which a file-level match misses (Q6, Q7).
- One conformance library that imports neither `package:test` nor `package:flutter_test`, holds its cases as values and asserts with `package:matcher/expect.dart` binds under `test` on the VM and under `testWidgets` with `pumpAndSettle` (Q8, Q10). `fvm flutter test --no-pub` runs a binding under `hsdd/` from the pure-Dart workspace root (Q10); `fvm dart test` cannot load it (Q12). A test-name prefix filter selects cases under both runners (Q9, Q11).
- A binding that imports a package absent from the workspace fails to load (Q13), and the workspace's package configuration tells that apart before anything runs (Q14). A member's own test can bind the same conformance library by relative import (Q15).
- `package:json_schema` 5.2.2 validates draft 2020-12 (`$defs`, `prefixItems`, `items: false`, `unevaluatedProperties`) in one resolution with Flutter and `test` (Q16). `fvm dart run {member}` works from the workspace root without the root depending on the member (Q17).
- A recorded-invocation input tree under `hsdd/` can enable an analysis server plugin through its own `analysis_options.yaml` by relative path, including a plugin that is a workspace member (Q18, Q19).

Planning the producing nodes settled three more facts that the replay tool's command line has to account for:

- `dart run` started from a recorded invocation's `files/` directory re-resolves a workspace whose resolution is older than a member's `pubspec.yaml`, and then fails with exit 255, which would read as the case's own exit code (`docs/auto-run/experiments/topic-codegen-invocations/`, the note in `run.sh` on copying the package with its modification times kept; nidana.model.7). Building the `cli` set showed what the fix has to be. On Dart 3.13.5 pub reads a workspace as fresh by modification times, only when every `pubspec.yaml` is no newer than `pubspec.lock` and `pubspec.lock` no newer than `.dart_tool/package_config.json`, and on a stale one `dart run {package}:{executable}` from `files/`, which holds no `pubspec.yaml`, looks for one there and exits 255 before the program starts. `dart pub get --enforce-lockfile` does not make such a workspace fresh. The executable's script, `bin/{executable}.dart`, started by the same `dart` with `--packages` naming the workspace's package configuration, starts on a stale workspace and prints what `dart run` prints (`docs/auto-run/experiments/file-cli-sets-plan/`, K1 to K8, M1 to M5 and N1 to N8; `docs/auto-run/experiments/sweep-adr-001/`, E).
- `dart test` given a name filter that admits no case prints "No tests ran." and exits 79 (`docs/auto-run/experiments/empty-guarantee-selection/`, E2). A restricted gate admits no case of some binding whenever the binding's guarantees are delivered later, as at nidana.navigation.2 to .5 and before nidana.flutter.7.
- Applied as a raw name filter, the bare bus-api@v1 ids of nidana.runtime.11's gate select topology-dsl@v1's live-suite cases G18 to G21, G24 and G29, which `bus_activation_test.dart` binds, before nidana.runtime.12 wires the pipeline (same experiment, E3, shown on two of those cases). A binding's restriction therefore has to be keyed by the slug whose suite it runs.

## Decision

Resolves OQ8. Contracts in this tree are validated as follows.

1. **Kinds.** `api` for a Dart library surface consumers import and call; `shared-model` for Dart value types consumers construct and match on; `schema` for a serialized data format; `file` for a generated file layout; `cli` for commands, diagnostics and exit codes.
2. **Location and analysis.** Fixtures live under `hsdd/contract/fixture/{slug}/`, schemas at `hsdd/contract/schema/{slug}.schema.json`. The workspace root's `analysis_options.yaml` excludes `hsdd/**`, so only the replay tool analyzes fixtures. `hsdd/contract/fixture/analysis_options.yaml` governs every fixture: no lint set; `strict-casts`, `strict-inference` and `strict-raw-types` on. Fixtures import public libraries only (`package:{name}/{library}.dart`, never `src/`), plus `package:matcher`, `package:test`, `package:flutter_test` and `package:nidana_contract_check/fixture.dart`, all resolved through the workspace's package configuration. A fixture's import and export directives carry no configuration (`if (...) '{uri}'`), because the replay tool reads only a directive's first URI (item 9). These options and this import rule bind the Dart libraries of `surface/`, `reject/` and `behavior/`, the only fixtures the replay tool analyzes. Input and expected trees (`input/`, `expected/`, `invocation/{case}/files/`, `invocation/{case}/expected/`) and data directories (item 9) are data, which the replay tool never analyzes, although a recorded command may analyze its own `files/`.
3. **Guarantee ids.** Each entry of a contract's `## Guarantees / invariants` list begins with a stable id, `- **G{n}** {statement}`. An id is never renumbered and never reused within its slug. Every guarantee is covered by at least one reject fixture, behavior case, schema set, file replay or recorded invocation, or appears in the contract's `## Validation` section as `- not executable: G{n}, {reason}; checked by {node}'s gates`.
   - `{ids}` below is a list of ids `G{n}` and ranges `G{a} to G{b}`, separated by `, ` or ` and `.
   - A reject fixture covers the ids its `// covers: {ids}` header names, and a behavior case the id its name begins with.
   - The schema set, the file replay and recorded invocations carry no id in their files, so `## Validation` declares what they cover. A `- schema:` or `- file:` bullet whose set covers guarantees ends with `covers {ids}.`. Every recorded invocation has one row in a table whose first column is `Case`, holding the case directory's name in backticks, and whose `Covers` cell begins with `{ids}`, optionally followed by `: ` and a note.
   - A guarantee covered only in part also has a not-executable line for the rest, which names that part: `- not executable: G{n}'s {part}, {reason}; checked by {node}'s gates`.
   - The structure set reads the id that begins a not-executable line and the node in `checked by {node}'s gates`; further text may follow.
4. **`api` and `shared-model` contracts** carry no schema file: the Interface's Dart declarations are the schema, made executable by these sets.
   - `surface/`: Dart libraries that use every declaration the Interface lists, writing out the types it states. A file passes when `fvm dart analyze --fatal-infos` reports no diagnostic on it.
   - `reject/`: one Dart library per type-level guarantee, or per misuse that breaks several. Its header names what it covers, `// covers: {ids}` (item 3). A comment on its own line, `// expect-diagnostic: {code}`, expects the diagnostic `{code}`, in lowercase as `dart analyze --format=json` reports it, on the next line. A file passes when the (line, code) pairs reported in it, at every severity, equal the pairs its markers name, and it has at least one marker.
   - `behavior/{subject}_conformance.dart`: conformance libraries. Each declares a harness interface, which is what an implementation supplies: factories for the implementation, and `Future<void> settle()` to bring it to quiescence. Each exports its cases as a value of type `List<ConformanceCase<H>>`. `ConformanceCase<H>` is the record `({String name, Future<void> Function(H harness) body})`, exported by `package:nidana_contract_check/fixture.dart`. Every name is a string literal that begins with the guarantee id, `'G{n} ...'`. A conformance library imports neither `package:test` nor `package:flutter_test`, and asserts with `package:matcher/expect.dart`. Every conformance library is imported by at least one binding, of its own contract or of another.
   - `behavior/{implementation}_test.dart`: bindings, one per implementation, named after the implementation in snake case. A binding imports exactly one conformance library, by relative path, and registers every case of it, with `test`, or with `testWidgets` for an implementation that needs the widget tree. A binding lives in the fixture directory of the contract whose Interface declares the implementation. When the interface belongs to another contract, the binding imports that contract's conformance library by relative path: bus-api@v2 declares the activation path, `Bus.activate` interpreting the `TopologyPlan` a declaration produces, so `hsdd/contract/fixture/bus-api/behavior/bus_activation_test.dart` binds topology-dsl@v2's live suite. The contract's `## Validation` section lists each binding with the implementation it binds.
   - An `api` contract with a serialized form (topology-ir@v1) also carries item 5's schema and edge cases. Its conformance library includes the round trip of every `valid/` file through the producer's decoder and encoder, and checks the producer's real output with `expectMatchesSchema` from `package:nidana_contract_check/fixture.dart`.
5. **`schema` contracts** carry a JSON Schema, draft 2020-12, and edge cases under `valid/` and `invalid/`. Every `valid/` file validates and no `invalid/` file does. The producer side is checked as item 4's serialized-form clause states.
6. **`file` contracts** carry `input/` and `expected/` trees. The contract's `## Validation` section names the generator command, with `{input}` and `{output}` placeholders, in a `- file:` bullet: the command is the one backticked span of the contract's `- file:` bullets that holds `{output}` and a space, so a span that holds `{output}` without a space, such as `{output}` alone, names no command. Its words, split at spaces, begin with `fvm dart` or `dart`, and the replay runs the rest with the `dart` running the replay tool. The replay runs it from the workspace root into an empty directory, formats the generated Dart with `fvm dart format`, and compares the result with `expected/` byte for byte, the file set included.
   - A `file` contract whose input is a data format (topic-codegen@v1's topics document) also carries item 5's schema and edge cases for that format.
   - A `file` contract may also carry item 7's recorded invocations, for what one input tree cannot show: its generator's other modes, its rejection of an input, its usage errors and their exit codes.
7. **`cli` contracts** carry one directory per recorded invocation, `invocation/{case}/`. It holds `args`: the command on the first line (`dart`, `flutter` or `{package}:{executable}`), then one argument per line. An argument `{output}` is replaced by a path inside a fresh temporary directory, at which nothing exists when the command starts. It may hold `files/`, an input tree that is the working directory; a case without `files/` runs from the workspace root. It holds `exit_code`, and optionally `stdout` and `stderr`, each compared exactly after the absolute paths of `{output}`, of `files/` and of the workspace root, each as given and symlink-resolved, are replaced by `{output}`, `{files}` and `{root}`, in that order. A case that needs the analysis server plugin enables it in `files/analysis_options.yaml` by a relative path to the plugin package.
   - A case whose `args` name `{output}` may hold `expected/`: after the run, the tree at `{output}` must equal it as item 6 compares. Without `expected/`, nothing may exist at `{output}` after the run.
   - `dart` is the `dart` running the replay tool, and `flutter` the `flutter` of that `dart`'s SDK, as for item 9's Flutter bindings. A `{package}:{executable}` command runs as `bin/{executable}.dart` below the root that the workspace's package configuration gives `{package}`, started by the `dart` running the tool with `--packages` naming the workspace root's `.dart_tool/package_config.json`, and never through `dart run`: from a `files/` directory, which holds no `pubspec.yaml`, `dart run` exits 255 before the program starts whenever pub reads the workspace as stale, as it does once a member `pubspec.yaml` is newer than `pubspec.lock`, and the comparison would read that exit as the case's, while the script form starts either way and prints what `dart run` prints. A `dart` command whose first argument is `run` runs as written, so a case with `files/` names a package's executable as `{package}:{executable}`; no set checks this.
   - The command runs in `files/` where it lies, under `hsdd/contract/fixture/`, not in a copy, since the plugin path in `files/analysis_options.yaml` is relative to it. The command leaves `files/` as it found it, writing and removing nothing there. The replay tool does not check this: a file a command leaves in `files/` stays there, and `git status` does not show it when `.gitignore` names it, as it names `.dart_tool/` and a `pubspec.lock` below the root.
   - The replay tool reads the plugins a case enables, for item 9's `PENDING`, as the keys at the first indentation of the top-level section of `files/analysis_options.yaml` that opens with a line that is exactly `plugins:`. A `plugins:` line that carries a comment or trailing space opens no section the tool reads, so the case runs, rather than being `PENDING`, when the plugin's package is absent. A case writes the line exactly `plugins:`; no set checks this.
8. **Authorship.** hsdd-contract writes every fixture, binding and schema, and `hsdd/contract/fixture/analysis_options.yaml`, when it authors a contract or a version, before the producing package exists. A phase never writes under `hsdd/contract/`.
9. **Replay tool.** `packages/nidana_contract_check`, not published, owned by nidana.model, with `package:json_schema` as a dependency. It lands by set over four of nidana.model's phases, each set before the first gate that runs it (nidana.model D1): `structure` at nidana.model.1; `surface`, `reject`, `schema`, `package:nidana_contract_check/fixture.dart` and PENDING detection at nidana.model.2; `behavior` at nidana.model.6; `file` and `cli` at nidana.model.7. A phase of another node whose gate runs a set, or whose tests import `fixture.dart`, depends on the phase that lands it. It runs from the workspace root as `fvm dart run nidana_contract_check {slug}... [--set {set},...] [--guarantee {id},...]`, or with `--all` for every slug that has a fixture directory.
   - Sets: `structure`, `surface`, `reject`, `behavior`, `schema`, `file`, `cli`. The default is every set the slug has. `structure` always runs first, whether `--set` names it or not, and needs no implementation: the contract text, UTF-8, with its frontmatter `id` and `kind` and its guarantee entries (item 3); marker and header syntax, and the case names of conformance libraries; item 3's forms in `## Validation` and its coverage, every cited id declared; the bindings listed in `## Validation` against the files present; the Case table's rows against the `invocation/` directories present; the fixture directory's layout; the ban on `src/` imports; item 4's ban on a conformance library that imports `package:test` or `package:flutter_test` (rule `conformance-import`); and every Dart library of `surface/`, `reject/` and `behavior/` UTF-8 (rule `encoding`). `--set` selects among a slug's other sets and never adds a set the slug lacks, so a slug that has none of the named sets, under `--all` or named, runs `structure` alone.
   - `structure` reads one slug and a directive's first URI, and leaves these rules to the `behavior` set or to reading. What a binding imports: a binding that imports no conformance library or more than one fails `behavior` (rule `suite`), so `--set structure` passes it. That a conformance library is bound: its case names count toward item 3's coverage whether or not a binding imports it. That a case has one row: the Case table's rows and the case directories are matched as sets, a second row naming a case counts toward coverage, and the `cli` set reads the case's ids from the first row. A directive's configurations: a URI after `if (...)` escapes the ban on `src/` imports, `conformance-import` and `PENDING`, so a binding that names an absent package there fails to load instead of being `PENDING`.
   - Layout: each entry directly under `hsdd/contract/fixture/{slug}/` is either a set directory that items 4 to 7 give the contract's kind (`surface/`, `reject/`, `behavior/`, `valid/`, `invalid/`, `input/`, `expected/`, `invocation/`) or a data directory. A data directory is listed in `## Validation` by a bullet `` - {dir}: `hsdd/contract/fixture/{slug}/{dir}/`, {what it holds and what reads it} ``. `structure` fails on any other entry and on a listed data directory that is absent. No set reads a data directory by itself: conformance cases read one by a path relative to the workspace root (topology-ir@v1's `render/` goldens), or a node's gates read it (topic-codegen@v1's `rejected/` documents).
   - `--guarantee` takes `{slug}/G{n}` and bare `G{n}`. A bare `G{n}` belongs to the one slug the command names, and is a usage error when the command replays more than one slug. A `{slug}/G{n}` may name a slug the command does not replay. The restriction leaves `structure`, `surface`, `reject` and `schema` unrestricted.
   - Under `--guarantee`, a binding runs only the cases whose names begin with an id of the slug whose conformance library it imports, which the tool reads from that import, so a binding whose suite's slug has no id in the restriction runs no case. A bare id therefore restricts only the bindings of the replayed slug's own suites: under a bus-api replay, `hsdd/contract/fixture/bus-api/behavior/bus_activation_test.dart`, which binds topology-dsl@v2's live suite, runs only the cases the restriction names by `topology-dsl/G{n}` ids.
   - Under `--guarantee`, a file replay or recorded invocation runs only when every id `## Validation` declares for it (item 3) is in the restriction, so a slug with no id of its own in the restriction runs none of them. A file replay's ids are those of the covers clauses of the contract's `- file:` bullets; a recorded invocation's are those of the first Case-table row that names it, and a later row that names it again is ignored. One that declares no id, a file replay whose `- file:` bullets carry no covers clause or a recorded invocation whose Covers cell is malformed, runs only unrestricted.
   - A binding, file replay or recorded invocation that the restriction admits no case of is not run and counts as passing. The tool never starts a test runner with a name filter that admits no case, because `dart test` then exits 79.
   - A fixture defect that the tool finds before running anything fails the fixture whether the restriction admits it or not, so a contract gap is loud at every gate: a binding or conformance library that cannot be read, a binding that imports no conformance library or more than one, a generator command, `args`, `exit_code`, `stdout` or `stderr` that cannot be read, and, for the `file` and `cli` sets, a contract text that is absent or not UTF-8. After that the sets differ. `file` and `cli` apply the restriction before `PENDING`, so a file replay or recorded invocation the restriction does not admit passes unrun even when a package it runs is absent. `behavior` reports `PENDING` before it applies the restriction, so a binding that imports an absent package, or whose conformance library does, is `PENDING` even when the restriction admits none of its cases.
   - A binding that imports `package:flutter_test` runs under `flutter test --no-pub`, any other under `dart test`, both from the workspace root, with the `flutter` that belongs to the SDK of the `dart` running the tool.
   - Before the `file` or `cli` set, the tool runs `dart pub get --enforce-lockfile` once at the workspace root, with the `dart` running the tool, before it reads the workspace's package configuration. The packages that `PENDING` and item 7's `{package}:{executable}` form then read are those of the committed lockfile, and a lockfile that no longer satisfies the pubspecs is an environment error of the `file` and `cli` sets before any of their cases runs. It does not make fresh a workspace that pub reads as stale by modification times, such as one whose member `pubspec.yaml` is newer than `pubspec.lock`, and no case needs it to: a file replay runs from the workspace root, where `dart run` starts on a stale workspace, and a recorded invocation runs a `{package}:{executable}` command as item 7 states.
   - A fixture that names a package absent from the workspace's package configuration fails, reported as `PENDING` rather than as a defect: a `surface`, `reject` or `behavior` library, a binding included, that imports the package, and a file replay or recorded invocation whose command runs it. The packages a file replay or recorded invocation runs are a `{package}:{executable}` command's package, the package of a `dart run` command's target (the first argument after `run` that does not start with `-`, read as `{package}` or `{package}:{executable}`), and every plugin that a recorded invocation's `files/analysis_options.yaml` enables (item 7).
   - The tool prints one line per fixture. It exits 0 when every fixture it runs passes; 1 when any fixture fails or is `PENDING`; 2 on an environment error, such as that `pub get` failing or no `flutter` in the SDK of the running `dart` for a Flutter binding; 64 on a usage error, such as an unknown slug or set, a malformed id, or a bare `G{n}` with more than one slug.
10. **Gates.** The gate of every phase that produces a contract includes `fvm dart run nidana_contract_check {slug}`. `structure`, `surface`, `reject` and `schema` run in full at every producing phase, because under `fp-progression` every declaration of a contract's Interface has landed when its first producing phase, the first phase of its producing leaf-parent that its `produced_by` names, merges, and a schema needs no implementation. That phase lands them, except a declaration that another contract's declarations name, which may have landed with that contract in an earlier phase of the same leaf-parent. The replay tool's phases (item 9) produce no contract, so the first producing phases of nidana.model's three contracts are nidana.model.3 to nidana.model.5, one per contract, not the node's first phase. `behavior`, `file` and `cli` run restricted by `--guarantee` to the guarantees the node's phases have delivered so far, cumulatively, and unrestricted at the last phase that produces the contract. nidana.integration's gate runs `--all`, unrestricted.
   - An `api` or `shared-model` contract has one producing leaf-parent. Its `surface` and `reject` sets run in full from its first producing phase, so every declaration they use, a declaration of another contract included, has landed when that phase merges. nidana.model.4, topology-dsl@v2's first producing phase, lands topology-ir@v1's main-library declarations, `TopologyDefinition` and those its signatures name, for topology-dsl@v2's surface; nidana.model.5, topology-ir@v1's, lands the rest of topology-ir@v1's Interface (nidana.model D1 item 2).
   - A contract of another kind may have more than one producing leaf-parent. The spec of the node whose decomposition gave it those producers names each producer's share of its guarantees, as nidana.tooling D2 does for nidana-checks@v1. A file replay or recorded invocation falls within a share when every id it covers is in that share, and each falls within exactly one share. One that declares no id runs only unrestricted (item 9), so it falls within no share and only nidana.integration's `--all` replays it; such a contract's cases each declare ids. Each producer's phases run `file` and `cli` restricted to the guarantees that producer's phases have delivered so far, cumulatively, and its last producing phase runs them restricted to its whole share instead of unrestricted. Those last replays together run every case. `structure` and `schema` run in full at every producing phase of every producer. The one unrestricted replay of such a contract is nidana.integration's `--all`.
11. **Consumers.** A consumer of an in-process `api` or `shared-model` contract builds against the producer's real package once the phase that the contract's Delivery paragraph names for a consumer's edge has merged (root D10): the contract's first producing phase, or a later type-level phase when contracts share one library, as topology-dsl@v2's consumers wait on nidana.model.5. A consumer that needs a stand-in binds the contract's conformance library to the stand-in in its own package's `test/` directory, importing the library by relative path, and runs that binding in its gate. A stand-in that does not pass the suite is not a fixture.
12. **What counts for `stable`.** A fixtures directory is this tree's executable validation artifact only when it meets item 3 and the items for its kind. The `structure` set checks this once the replay tool exists; until then the hsdd-contract author and hsdd-reconcile check it by reading, and they still check by reading what item 9 says `structure` leaves to reading.

## Consequences

- No contract replay can run before nidana.model.1 merges the `structure` set, no other set before the phase item 9 names for it, and no conformance library loads before nidana.model.2 merges `package:nidana_contract_check/fixture.dart`. Every fixture written before its set lands is unverified, reject codes above all, so the first replay against each producer can fail on the fixture itself; that is a contract gap, renegotiated through hsdd-contract mid-phase.
- The workspace root's `analysis_options.yaml` (ADR-002) excludes `hsdd/**` beside `ref/**` and `docs/**`. A workspace-wide `fvm dart analyze` never reports on a fixture; a fixture's diagnostics come from the replay tool only.
- `package:json_schema` joins the workspace's single resolution through the replay tool.
- Every contract's guarantees carry `G{n}` ids. Phase plans cite them in `--guarantee` restrictions, and verification docs cite them.
- A contract whose Interface declares an implementation of another contract's interface carries that binding: bus-api@v2 for topology-dsl@v2's live suite, which its activation path implements, and flutter-binding@v2 for navigation-api@v1's executor protocol, which `FlutterNavigationExecutor` implements. Its producer's gate therefore runs the other contract's suite, and its authoring step needs the other contract's conformance library to exist first.
- What a schema set, a file replay or a recorded invocation covers, which data directories a fixture tree holds, and which guarantees are executable only in part are read from the contract's `## Validation` section, so the forms of items 3 and 9 are part of every contract's text. A misspelt set directory fails `structure` instead of going unreplayed.
- The replay tool's `cli` set carries the `{output}` argument and reuses the `file` set's tree comparison, so a generator's rejections, its other modes and its exit codes are executable as recorded invocations of its `file` contract. A guarantee about them stays not executable only while its contract carries no such case.
- `--guarantee` restricts file replays and recorded invocations by their declared ids, so a node that delivers a generator or a checker over several phases replays, at each gate, only what it has delivered.
- A contract with more than one producing leaf-parent, nidana-checks@v1 today, is replayed unrestricted only by nidana.integration's `--all`. Each producer's last gate runs the cases of its own share, so no producer waits on another. A case whose ids span two shares, or fall within none, would have no producing gate to replay it, and the replay tool cannot see the shares, which live in a node spec. Whoever adds a case to such a contract (hsdd-contract) or plans one of its producers (hsdd-phase-plan) checks by reading that each case falls within exactly one share.
- An `api` or `shared-model` contract cannot be split between leaf-parents without changing item 10 first.
- A Flutter binding runs from the pure-Dart workspace root; no member has to host it.
- Replaying a contract whose producing package is absent from the workspace reports every fixture that names the package as `PENDING` and exits 1, so a gate placed before the phase that creates the package fails instead of passing. A contract's sets other than `structure` and `schema` are replayed from its first producing phase on, by which time the package exists.
- A restricted gate passes a binding whose cases are all delivered after it, unless the binding or its conformance library imports a package absent at that gate, which item 9's order makes `PENDING` and the gate fail. A producer that implements another contract's interface, as nidana.runtime implements topology-dsl@v2's activation path, replays that contract's cases at a restricted gate only as the gate names them by `{slug}/G{n}`.
- A changed guarantee changes the fixtures, and every binding of the suite, a consumer's stand-in included, fails loudly instead of drifting.
- Some rules here bind the fixtures' author while no set checks them: every conformance library bound (item 4), one Case-table row per recorded invocation (item 3), no configuration on a fixture directive (item 2), and a recorded invocation that leaves `files/` as it found it, writes its `plugins:` line exactly, and names a package's executable as `{package}:{executable}` when it has `files/` (item 7). hsdd-contract checks them by reading when it writes a fixture. That a binding imports exactly one conformance library only `behavior` checks, so `--all --set structure`, the replay an hsdd-contract author runs, passes a binding that imports none or two. A set that checked any of these would change the replay tool, not this decision.
- No fixture format here is language-neutral. Cross-platform test parity (Guide §10.1) needs its own decision when a second platform port starts.

## Alternatives considered

- **Language-neutral scenario fixtures** (JSON scenarios run by an interpreter on each platform). They would also answer Guide §10.1's parity question, but need a scenario vocabulary and an interpreter before any gate can run, and cannot express type-level guarantees. The signal that would favor them: a second platform port starting within v1.
- **Public API snapshots diffed by a tool.** They pin signatures, but no behavior and no type-level misuse.
- **A file-level `// expect-diagnostic:` header matched anywhere in the file, checking errors only** (the wording the root decomposition proposed). It passes a marker on the wrong line and cannot pin a warning-severity guarantee such as `@visibleForTesting` (Q2, Q7).
- **Conformance libraries that register their own tests with `package:test`.** They cannot reach a `WidgetTester`, so an implementation that needs the widget tree would need a second suite, and two suites drift.
- **Bindings in each implementing package's `test/`, written by its phases.** A phase could bind a subset of the cases, and HSDD keeps fixtures out of phase hands. Only a consumer's stand-in, which no contract declares, is bound that way (item 11).
- **Skipping a binding whose package is absent.** A renamed or missing package would then pass a gate silently.
- **JSON Schema draft-07.** Wider tool support, but no `unevaluatedProperties`, so a closed object composed from `$defs` cannot be stated.
- **Several `input/{case}/` and `expected/{case}/` pairs in item 6, each with its own arguments and exit code** (the shape the topic-codegen@v1 authoring step proposed). It repeats item 7's `args` and `exit_code` in a second layout that the replay tool would run with a second runner; item 7 with `{output}` gives the same cases from parts the tool has anyway.
- **Generator failures left to the producing node's gates in v1.** It costs nothing now, and the cases could be added later as a compatible change, but phases would then write them after the producer instead of before it, and nidana.integration's `--all` gate would not replay them. The signal that would favor it: the replay tool not fitting nidana.model's first phase.
- **A `covers` file in each recorded invocation**, as a reject fixture carries its ids in its header. It keeps coverage beside the fixture, but repeats the table every `cli` contract's `## Validation` already holds, and two copies drift.
- **Data directories ignored by `structure`, or a fixed list of their names in this decision.** Ignoring them lets a misspelt set directory go unreplayed and pass; a fixed list needs an ADR change for every new data directory.
- **For two producers, the literal reading of "unrestricted at the last phase that produces the contract"**, where the producer whose last phase merges second replays every case. Its gate would run the other producer's cases, so it would need an ordering edge on the other producer that no contract carries, and which producer carries the edge would depend on merge order.
- **Shares declared in the contract's `## Validation`**, where `structure` could check that each case falls within exactly one. A contract is written before its producers are decomposed and names only its owner (nidana-checks@v1 leaves the division of its hosts to that decomposition), so every decomposition would need a contract touch to write the shares. The signal that would favor it: a contract with several producers whose cases change often enough that a case spanning two shares slips past reading.
- **`api` contracts with several producers, each replaying `surface` and `reject` over its own declarations.** `--guarantee` restricts neither set, so each surface and reject library would need a producer mark that no set reads.
- **A conformance library that no binding imports covers nothing** (a reading of item 3 that the plan of the `behavior` set routed to this ADR, DEC-1271). It would catch a suite that runs at no gate, but `structure` would need every slug's bindings to judge one slug, and the shipped tool counts such a library's cases. Item 4 makes every conformance library bound instead, checked by reading. The signal that would favor it: a contract authored with a suite no binding imports.
- **One order of the restriction and `PENDING` for every set.** Restriction first everywhere would let a restricted gate pass a binding whose package is absent, as `file` and `cli` do for their cases, which nidana-checks@v1's two producers rely on; `PENDING` first everywhere would make those producers' gates wait on each other's packages. Either would change a shipped set, so item 9 states each set's order as it ships.
