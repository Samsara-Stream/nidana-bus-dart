# ADR-001: Executable validation for Dart API contracts

## Context

HSDD lets a contract be `stable` only when it carries an executable validation artifact, a schema or a fixtures directory, at its canonical paths. The gate of every producing phase replays that artifact, and consumers build against the fixtures instead of hand-rolled mocks. HSDD's per-kind defaults (a schema plus example payloads for `api`, a schema plus edge cases for `shared-model`) fit wire formats. Most contracts in this tree are Dart library surfaces instead (root contract matrix): topic-model@v1 is `shared-model`; topology-dsl@v1, topology-ir@v1, bus-api@v1, bus-testing@v1, navigation-api@v1 and flutter-binding@v1 are `api`; topic-codegen@v1 is `file`; nidana-checks@v1 is `cli`. Their guarantees come in two sorts. Some are type-level, because the Specification makes the misuse a compile error: an event topic has no current value (Spec §2.5), an observer has no publish path (Spec §3.7), a read handle has no synchronous value (Spec §6.1). The rest are behavioral, above all the Bus Runtime Contract (Spec §3). Root OQ8 asks what executable validation means for such contracts.

Three properties of the setting shape the answer:

- Contracts and their fixtures are authored before any producing package exists. A fixture is a forward reference until the producer's first phase lands its type-level skeleton (root D10, ordering policy `fp-progression`).
- One interface can have implementations that need different test runners. The navigation executor protocol is implemented on the VM by an in-memory router and in Flutter by `FlutterNavigationExecutor`.
- The repository is one pub workspace whose root also holds `hsdd/` (ADR-002).

The experiment `docs/auto-run/experiments/contract-fixtures/` (`run.sh`, captured in `output.txt`) reproduces that layout on the pinned SDK (Flutter 3.47.7, Dart 3.13.5) and settles the runtime facts this decision uses:

- `analyzer: exclude: [hsdd/**]` in the root `analysis_options.yaml` keeps fixtures out of a workspace-wide `fvm dart analyze`, while an explicit path into `hsdd/` is still analyzed (Q1, Q2). A nested `hsdd/contract/fixture/analysis_options.yaml` replaces the root's lint set for every fixture; without it, the root's `depend_on_referenced_packages` fires on every fixture import, because fixtures belong to the root package.
- `fvm dart analyze --format=json` reports each diagnostic's code in lowercase, the spelling `// ignore:` comments use, with its 1-based line, at every severity: errors, warnings such as `invalid_use_of_visible_for_testing_member`, and infos (Q2, Q3). With `--fatal-infos`, a deprecated member fails a surface fixture; with the strict language modes, so do raw types and inference failures (Q5).
- A reject fixture written without running the analyzer can name the wrong code: the plausible `final_class_extended_outside_of_library` is reported as `invalid_use_of_type_outside_library` (Q7). Matching each expected code to a line also catches a marker on the wrong line and extra diagnostics, which a file-level match misses (Q6, Q7).
- One conformance library that imports neither `package:test` nor `package:flutter_test`, holds its cases as values and asserts with `package:matcher/expect.dart` binds under `test` on the VM and under `testWidgets` with `pumpAndSettle` (Q8, Q10). `fvm flutter test --no-pub` runs a binding under `hsdd/` from the pure-Dart workspace root (Q10); `fvm dart test` cannot load it (Q12). A test-name prefix filter selects cases under both runners (Q9, Q11).
- A binding that imports a package absent from the workspace fails to load (Q13), and the workspace's package configuration tells that apart before anything runs (Q14). A member's own test can bind the same conformance library by relative import (Q15).
- `package:json_schema` 5.2.2 validates draft 2020-12 (`$defs`, `prefixItems`, `items: false`, `unevaluatedProperties`) in one resolution with Flutter and `test` (Q16). `fvm dart run {member}` works from the workspace root without the root depending on the member (Q17).
- A recorded-invocation input tree under `hsdd/` can enable an analysis server plugin through its own `analysis_options.yaml` by relative path, including a plugin that is a workspace member (Q18, Q19).

## Decision

Resolves OQ8. Contracts in this tree are validated as follows.

1. **Kinds.** `api` for a Dart library surface consumers import and call; `shared-model` for Dart value types consumers construct and match on; `schema` for a serialized data format; `file` for a generated file layout; `cli` for commands, diagnostics and exit codes.
2. **Location and analysis.** Fixtures live under `hsdd/contract/fixture/{slug}/`, schemas at `hsdd/contract/schema/{slug}.schema.json`. The workspace root's `analysis_options.yaml` excludes `hsdd/**`, so only the replay tool analyzes fixtures. `hsdd/contract/fixture/analysis_options.yaml` governs every fixture: no lint set; `strict-casts`, `strict-inference` and `strict-raw-types` on. Fixtures import public libraries only (`package:{name}/{library}.dart`, never `src/`), plus `package:matcher`, `package:test`, `package:flutter_test` and `package:nidana_contract_check/fixture.dart`, all resolved through the workspace's package configuration. These options and this import rule bind the Dart libraries of `surface/`, `reject/` and `behavior/`, the only fixtures the replay tool analyzes. Input and expected trees (`input/`, `expected/`, `invocation/{case}/files/`, `invocation/{case}/expected/`) and data directories (item 9) are data, which the replay tool never analyzes, although a recorded command may analyze its own `files/`.
3. **Guarantee ids.** Each entry of a contract's `## Guarantees / invariants` list begins with a stable id, `- **G{n}** {statement}`. An id is never renumbered and never reused within its slug. Every guarantee is covered by at least one reject fixture, behavior case, schema set, file replay or recorded invocation, or appears in the contract's `## Validation` section as `- not executable: G{n}, {reason}; checked by {node}'s gates`.
   - `{ids}` below is a list of ids `G{n}` and ranges `G{a} to G{b}`, separated by `, ` or ` and `.
   - A reject fixture covers the ids its `// covers: {ids}` header names, and a behavior case the id its name begins with.
   - The schema set, the file replay and recorded invocations carry no id in their files, so `## Validation` declares what they cover. A `- schema:` or `- file:` bullet whose set covers guarantees ends with `covers {ids}.`. Every recorded invocation has one row in a table whose first column is `Case`, holding the case directory's name in backticks, and whose `Covers` cell begins with `{ids}`, optionally followed by `: ` and a note.
   - A guarantee covered only in part also has a not-executable line for the rest, which names that part: `- not executable: G{n}'s {part}, {reason}; checked by {node}'s gates`.
   - The structure set reads the id that begins a not-executable line and the node in `checked by {node}'s gates`; further text may follow.
4. **`api` and `shared-model` contracts** carry no schema file: the Interface's Dart declarations are the schema, made executable by these sets.
   - `surface/`: Dart libraries that use every declaration the Interface lists, writing out the types it states. A file passes when `fvm dart analyze --fatal-infos` reports no diagnostic on it.
   - `reject/`: one Dart library per type-level guarantee, or per misuse that breaks several. Its header names what it covers, `// covers: {ids}` (item 3). A comment on its own line, `// expect-diagnostic: {code}`, expects the diagnostic `{code}`, in lowercase as `dart analyze --format=json` reports it, on the next line. A file passes when the (line, code) pairs reported in it, at every severity, equal the pairs its markers name, and it has at least one marker.
   - `behavior/{subject}_conformance.dart`: conformance libraries. Each declares a harness interface, which is what an implementation supplies: factories for the implementation, and `Future<void> settle()` to bring it to quiescence. Each exports its cases as a value of type `List<ConformanceCase<H>>`. `ConformanceCase<H>` is the record `({String name, Future<void> Function(H harness) body})`, exported by `package:nidana_contract_check/fixture.dart`. Every name is a string literal that begins with the guarantee id, `'G{n} ...'`. A conformance library imports neither `package:test` nor `package:flutter_test`, and asserts with `package:matcher/expect.dart`.
   - `behavior/{implementation}_test.dart`: bindings, one per implementation, named after the implementation in snake case. A binding registers every case of one conformance library, with `test`, or with `testWidgets` for an implementation that needs the widget tree. A binding lives in the fixture directory of the contract whose Interface declares the implementation. When the interface belongs to another contract, the binding imports that contract's conformance library by relative path: bus-api@v1 declares the activation path, `Bus.activate` interpreting the `TopologyPlan` a declaration produces, so `hsdd/contract/fixture/bus-api/behavior/bus_activation_test.dart` binds topology-dsl@v1's live suite. The contract's `## Validation` section lists each binding with the implementation it binds.
   - An `api` contract with a serialized form (topology-ir@v1) also carries item 5's schema and edge cases. Its conformance library includes the round trip of every `valid/` file through the producer's decoder and encoder, and checks the producer's real output with `expectMatchesSchema` from `package:nidana_contract_check/fixture.dart`.
5. **`schema` contracts** carry a JSON Schema, draft 2020-12, and edge cases under `valid/` and `invalid/`. Every `valid/` file validates and no `invalid/` file does. The producer side is checked as item 4's serialized-form clause states.
6. **`file` contracts** carry `input/` and `expected/` trees. The contract's `## Validation` section names the generator command, with `{input}` and `{output}` placeholders. The replay runs it from the workspace root into an empty directory, formats the generated Dart with `fvm dart format`, and compares the result with `expected/` byte for byte, the file set included.
   - A `file` contract whose input is a data format (topic-codegen@v1's topics document) also carries item 5's schema and edge cases for that format.
   - A `file` contract may also carry item 7's recorded invocations, for what one input tree cannot show: its generator's other modes, its rejection of an input, its usage errors and their exit codes.
7. **`cli` contracts** carry one directory per recorded invocation, `invocation/{case}/`. It holds `args`: the command on the first line (`dart`, `flutter` or `{package}:{executable}`), then one argument per line. An argument `{output}` is replaced by a path inside a fresh temporary directory, at which nothing exists when the command starts. It may hold `files/`, an input tree that becomes the working directory; a case without `files/` runs from the workspace root. It holds `exit_code`, and optionally `stdout` and `stderr`, each compared exactly after the absolute paths of `{output}`, of `files/` and of the workspace root, each as given and symlink-resolved, are replaced by `{output}`, `{files}` and `{root}`, in that order. A case that needs the analysis server plugin enables it in `files/analysis_options.yaml` by a relative path to the plugin package.
   - A case whose `args` name `{output}` may hold `expected/`: after the run, the tree at `{output}` must equal it as item 6 compares. Without `expected/`, nothing may exist at `{output}` after the run.
8. **Authorship.** hsdd-contract writes every fixture, binding and schema, and `hsdd/contract/fixture/analysis_options.yaml`, when it authors a contract or a version, before the producing package exists. A phase never writes under `hsdd/contract/`.
9. **Replay tool.** `packages/nidana_contract_check`, not published, owned by nidana.model and written in its first phase, with `package:json_schema` as a dependency. It runs from the workspace root as `fvm dart run nidana_contract_check {slug}... [--set {set},...] [--guarantee {id},...]`, or with `--all` for every slug that has a fixture directory.
   - Sets: `structure`, `surface`, `reject`, `behavior`, `schema`, `file`, `cli`. The default is every set the slug has. `structure` always runs first and needs no implementation: marker and header syntax, item 3's coverage, the bindings listed in `## Validation` against the files present, the fixture directory's layout, and the ban on `src/` imports.
   - Layout: each entry directly under `hsdd/contract/fixture/{slug}/` is either a set directory that items 4 to 7 give the contract's kind (`surface/`, `reject/`, `behavior/`, `valid/`, `invalid/`, `input/`, `expected/`, `invocation/`) or a data directory. A data directory is listed in `## Validation` by a bullet `` - {dir}: `hsdd/contract/fixture/{slug}/{dir}/`, {what it holds and what reads it} ``. `structure` fails on any other entry and on a listed data directory that is absent. No set reads a data directory by itself: conformance cases read one by a path relative to the workspace root (topology-ir@v1's `render/` goldens), or a node's gates read it (topic-codegen@v1's `rejected/` documents).
   - `--guarantee` takes `{slug}/G{n}`; a bare `G{n}` means the slug being replayed. It restricts behavior cases by name prefix, and the file replay and recorded invocations by the ids `## Validation` declares for them (item 3): such a case runs only when every id it covers is in the restriction. It leaves `structure`, `surface`, `reject` and `schema` unrestricted. The tool learns which suite a binding runs from the conformance library the binding imports.
   - A binding that imports `package:flutter_test` runs under `flutter test --no-pub`, any other under `dart test`, both from the workspace root, with the `flutter` that belongs to the SDK of the `dart` running the tool.
   - A binding that imports a package absent from the workspace's package configuration fails, reported as `PENDING` rather than as a test failure.
   - The tool prints one line per fixture and exits non-zero on any failure.
10. **Gates.** The gate of every phase that produces a contract includes `fvm dart run nidana_contract_check {slug}`. `structure`, `surface`, `reject` and `schema` run in full at every producing phase, because the first phase of the producing leaf-parent lands every declaration under `fp-progression` and a schema needs no implementation. `behavior`, `file` and `cli` run restricted by `--guarantee` to the guarantees the node's phases have delivered so far, cumulatively, and unrestricted at the last phase that produces the contract. nidana.integration's gate runs `--all`, unrestricted.
   - An `api` or `shared-model` contract has one producing leaf-parent. Its `surface` and `reject` sets run in full from the first producing phase, so one first phase must land every declaration they use.
   - A contract of another kind may have more than one producing leaf-parent. The spec of the node whose decomposition gave it those producers names each producer's share of its guarantees, as nidana.tooling D2 does for nidana-checks@v1. A file replay or recorded invocation falls within a share when every id it covers is in that share, and each falls within exactly one share. Each producer's phases run `file` and `cli` restricted to the guarantees that producer's phases have delivered so far, cumulatively, and its last producing phase runs them restricted to its whole share instead of unrestricted. Those last replays together run every case. `structure` and `schema` run in full at every producing phase of every producer. The one unrestricted replay of such a contract is nidana.integration's `--all`.
11. **Consumers.** A consumer of an in-process `api` or `shared-model` contract builds against the producer's real package once the producer's first phase has merged (root D10). A consumer that needs a stand-in binds the contract's conformance library to the stand-in in its own package's `test/` directory, importing the library by relative path, and runs that binding in its gate. A stand-in that does not pass the suite is not a fixture.
12. **What counts for `stable`.** A fixtures directory is this tree's executable validation artifact only when it meets item 3 and the items for its kind. The `structure` set checks this once the replay tool exists; until then the hsdd-contract author and hsdd-reconcile check it by reading.

## Consequences

- No contract replay can run until nidana.model's first phase merges the replay tool and `package:nidana_contract_check/fixture.dart`. Every fixture written before then is unverified, reject codes above all, so the first replay against each producer can fail on the fixture itself; that is a contract gap, renegotiated through hsdd-contract mid-phase.
- The workspace root's `analysis_options.yaml` (ADR-002) excludes `hsdd/**` beside `ref/**` and `docs/**`. A workspace-wide `fvm dart analyze` never reports on a fixture; a fixture's diagnostics come from the replay tool only.
- `package:json_schema` joins the workspace's single resolution through the replay tool.
- Every contract's guarantees carry `G{n}` ids. Phase plans cite them in `--guarantee` restrictions, and verification docs cite them.
- A contract whose Interface declares an implementation of another contract's interface carries that binding: bus-api@v1 for topology-dsl@v1's live suite, which its activation path implements, and flutter-binding@v1 for navigation-api@v1's executor protocol, which `FlutterNavigationExecutor` implements. Its producer's gate therefore runs the other contract's suite, and its authoring step needs the other contract's conformance library to exist first.
- What a schema set, a file replay or a recorded invocation covers, which data directories a fixture tree holds, and which guarantees are executable only in part are read from the contract's `## Validation` section, so the forms of items 3 and 9 are part of every contract's text. A misspelt set directory fails `structure` instead of going unreplayed.
- The replay tool's `cli` set carries the `{output}` argument and reuses the `file` set's tree comparison, so a generator's rejections, its other modes and its exit codes are executable as recorded invocations of its `file` contract. A guarantee about them stays not executable only while its contract carries no such case.
- `--guarantee` restricts file replays and recorded invocations by their declared ids, so a node that delivers a generator or a checker over several phases replays, at each gate, only what it has delivered.
- A contract with more than one producing leaf-parent, nidana-checks@v1 today, is replayed unrestricted only by nidana.integration's `--all`. Each producer's last gate runs the cases of its own share, so no producer waits on another. A case whose ids span two shares, or fall within none, would have no producing gate to replay it, and the replay tool cannot see the shares, which live in a node spec. Whoever adds a case to such a contract (hsdd-contract) or plans one of its producers (hsdd-phase-plan) checks by reading that each case falls within exactly one share.
- An `api` or `shared-model` contract cannot be split between leaf-parents without changing item 10 first.
- A Flutter binding runs from the pure-Dart workspace root; no member has to host it.
- Replaying a contract before its producer's first phase has merged fails with `PENDING`, so no gate replays a contract whose producer is absent.
- A changed guarantee changes the fixtures, and every binding of the suite, a consumer's stand-in included, fails loudly instead of drifting.
- No fixture format here is language-neutral. Cross-platform test parity (Guide §10.1) needs its own decision when a second platform port starts.

## Alternatives considered

- **Language-neutral scenario fixtures** (JSON scenarios run by an interpreter on each platform). They would also answer Guide §10.1's parity question, but need a scenario vocabulary and an interpreter before any gate can run, and cannot express type-level guarantees. The signal that would favor them: a second platform port starting within v1.
- **Public API snapshots diffed by a tool.** They pin signatures, but no behavior and no type-level misuse.
- **A file-level `// expect-diagnostic:` header matched anywhere in the file, checking errors only** (the wording the root decomposition proposed). It passes a marker on the wrong line and cannot pin a warning-severity guarantee such as `@visibleForTesting` (Q2, Q7).
- **Conformance libraries that register their own tests with `package:test`.** They cannot reach a `WidgetTester`, so an implementation that needs the widget tree would need a second suite, and two suites drift.
- **Bindings in each implementing package's `test/`, written by its phases.** A phase could bind a subset of the cases, and HSDD keeps fixtures out of phase hands. Only a consumer's stand-in, which no contract declares, is bound that way (item 11).
- **Skipping a binding whose package is absent.** A renamed or missing package would then pass a gate silently.
- **JSON Schema draft-07.** Wider tool support, but no `unevaluatedProperties`, so a closed object composed from `$defs` cannot be stated.
- **Several `input/{case}/` and `expected/{case}/` pairs in item 6, each with its own arguments and exit code** (the shape the topic-codegen@v1 authoring step proposed). It repeats item 7's `args` and `exit_code` in a second layout that the replay tool would run with a second runner; item 7 with `{output}` gives the same cases from parts the tool has anyway.
- **Generator failures left to the producing node's gates in v1.** It costs nothing now, and the cases could be added later as a compatible change, but phases would then write them after the producer instead of before it, and nidana.integration's `--all` gate would not replay them. The signal that would favor it: the replay tool not fitting nidana.model's first phase.
- **A `covers` file in each recorded invocation**, as a reject fixture carries its ids in its header. It keeps coverage beside the fixture, but repeats the table every `cli` contract's `## Validation` already holds, and two copies drift.
- **Data directories ignored by `structure`, or a fixed list of their names in this decision.** Ignoring them lets a misspelt set directory go unreplayed and pass; a fixed list needs an ADR change for every new data directory.
- **For two producers, the literal reading of "unrestricted at the last phase that produces the contract"**, where the producer whose last phase merges second replays every case. Its gate would run the other producer's cases, so it would need an ordering edge on the other producer that no contract carries, and which producer carries the edge would depend on merge order.
- **Shares declared in the contract's `## Validation`**, where `structure` could check that each case falls within exactly one. A contract is written before its producers are decomposed and names only its owner (nidana-checks@v1 leaves the division of its hosts to that decomposition), so every decomposition would need a contract touch to write the shares. The signal that would favor it: a contract with several producers whose cases change often enough that a case spanning two shares slips past reading.
- **`api` contracts with several producers, each replaying `surface` and `reject` over its own declarations.** `--guarantee` restricts neither set, so each surface and reject library would need a producer mark that no set reads.

## Amendments

- 2026-10-17, amended in place after the nine root contracts were written in this format. The decision keeps its kinds, its sets, its replay tool and every item number; the amendment adds what those contracts needed and the accepted text lacked.
  - Item 2: the analysis options and the import rule bind the libraries of `surface/`, `reject/` and `behavior/` only; input and expected trees and data directories are never analyzed.
  - Item 3: coverage by the schema set, the file replay and recorded invocations, declared in `## Validation`; the `{ids}` list form; the not-executable line for a guarantee covered in part.
  - Item 4: `// covers: {ids}`; the cross-contract binding example names bus-api@v1's activation path, because topology-dsl@v1 replaced the live topology builder with a `TopologyPlan` that activation interprets.
  - Item 6: the file set is part of the comparison; a `file` contract's input format carries a schema; a `file` contract may carry recorded invocations.
  - Item 7: a case without `files/` runs from the workspace root; `{output}` and `expected/`; symlink-resolved paths.
  - Item 9: the layout check and data directories; `--guarantee` over file replays and recorded invocations.
  - Item 10: `schema` runs in full; `file` and `cli` run restricted like `behavior`.
  - Consequences: the cross-contract binding bullet, and three new bullets.
  - Evidence: the `## Validation` sections of topology-ir@v1, topic-codegen@v1 and nidana-checks@v1; `docs/auto-run/experiments/file-invocations/` (`run.sh`, `output.txt`), where sixteen candidate recorded invocations of topic-codegen@v1's `generate`, with `{output}` and `expected/`, passed against the stand-in generator and four seeded defects each failed; and `structure.sh` there (`structure-output.txt`), where a prototype of the amended coverage and layout checks passed all nine contracts as written and reported each seeded defect.
  - Not superseded: the decision did not change, contracts cite its items by number, and a superseding ADR would move every `Governed by` link without changing what binds.
- 2026-10-18, amended in place after nidana.tooling's decomposition (nidana.tooling D1) gave nidana-checks@v1 two producing leaf-parents: nidana.tooling.lint for the plugin's cases, nidana.tooling.codegen for the scan's. Item 10's "unrestricted at the last phase that produces the contract" had no single reading for two producers.
  - Item 10: two sub-bullets. An `api` or `shared-model` contract has one producing leaf-parent, which every such contract in this tree already has. A contract of another kind with several producers is replayed per producer within the share of its guarantees that the deciding node spec names; each case falls within exactly one share; each producer's last producing phase runs restricted to its whole share; nidana.integration's `--all` is the one unrestricted replay. This is nidana.tooling D2's reading, stated for any such contract.
  - Frontmatter `affects`: nidana.tooling.codegen and nidana.tooling.lint, whose specs already carry `Governed by: [ADR-001, ADR-002]`. nidana.tooling stays, because its spec carries the link and its D2 reads item 10.
  - Consequences: two new bullets. Alternatives considered: three new entries.
  - Evidence: nidana.tooling D2; nidana-checks@v1's Validation table, where each of the seventeen cases falls within exactly one share, the eight `analyze-*` cases within nidana.tooling.lint's G1 to G8 and the nine `scan-*` cases within nidana.tooling.codegen's G3 and G9 to G18 (their Covers cells checked against both shares); the nine contracts' `kind` and `produced_by`, where every `api` and `shared-model` contract is produced by one leaf-parent.
  - Not superseded, for the same reasons as the first amendment: no item number moved, and no fixture, contract or `Governed by` link changes.
